# AGENTS.md — `hivemind-audio-binary-protocol`

Guidance for AI coding agents (and humans) working in this repository. Read it
fully before making changes. It encodes conventions that are not obvious from the
code and that, if ignored, produce work that will be rejected.

## Repo

Binary audio plugin for [HiveMind-core](https://github.com/JarbasHiveMind/HiveMind-core):
it adds server-side WakeWord detection, VAD, STT, and TTS to a hivemind-core hub, so
lightweight satellites can stream raw PCM audio to the hub and receive transcriptions
or synthesized speech without running any models locally. It registers under the
`hivemind.binary.protocol` entry-point group and is loaded at runtime by
[hivemind-plugin-manager](https://github.com/JarbasHiveMind/hivemind-plugin-manager)'s
`BinaryDataHandlerFactory`. This transport is homelab-only by design — raw audio
streaming is not meant to cross the open internet, only a trusted local network or
tailnet. Related repos: the hub
([HiveMind-core](https://github.com/JarbasHiveMind/HiveMind-core)), the plugin loader
([hivemind-plugin-manager](https://github.com/JarbasHiveMind/hivemind-plugin-manager)),
and the reference satellite
([hivemind-mic-satellite](https://github.com/JarbasHiveMind/hivemind-mic-satellite)).

## Layout / build / test

- Package module: `hivemind_audio_binary_protocol/` (`protocol.py` is the entry-point
  target, `transformers.py` holds the audio transformer glue). Tests live in `tests/`
  (`tests/test_audio_format.py` unit tests, `tests/e2e/` runs an in-process HiveMind
  topology via `hivescope`) — do not create a second test directory.
- Set up a throwaway environment inside your clone; never touch a shared venv:
  `python3 -m venv .venv && VIRTUAL_ENV=$PWD/.venv uv pip install -e ".[test]" --prerelease=allow`
- Run the suite in the foreground: `python3 -m pytest tests -q`. The e2e suite spins up
  a simulated hub/satellite topology through `hivescope` (declared as a test-only
  dependency even though it also supplies `hivemind-core`, an AGPL package this plugin
  imports from at runtime but only ever receives from the server that loads it).
- `uv`, never `pip`. If latest prereleases fail to install or resolve, that is a bug to
  FIX at the source, not to work around with a pin downgrade.

## Tests

- Adversarial by default. A regression test must **fail before the fix and pass
  after** — prove it by reverting only the source (`git apply -R`, never
  `git stash` across worktrees) and watching the test flip.
- Tests must be mutation-proof: gutting the feature must fail the test. A test
  that only asserts a mock was called, without asserting the real behaviour, is
  weak — note it.
- Never skip a test because an optional dependency is missing.
- CI green is permission to review, not to merge. A non-trivial change gets an
  adversarial review before it lands.

## Repo-specific rules

- Wire back-compat is law: deployed satellites and hubs run mismatched
  versions of this plugin and of `hivemind-core`. Do not change the binary
  frame layout, the three streaming modes (mic stream, STT transcription, STT
  handle), or the config schema in a way that breaks an already-deployed
  client or hub — extend, do not replace.
- Never add a new bus message type. Reuse the existing `recognizer_loop:*` and
  `speak:*` events this plugin already emits and consumes.
- This is a binary audio transport, not the websocket control transport — but
  it must still honor the hub's client ACLs (per-client `allowed_types`, the
  same access-control surface the websocket transport enforces). If you touch
  ACL handling, keep the semantics identical to how HiveMind-core interprets
  them for other transports; do not invent a parallel access model here.
- Treat this plugin as homelab-only: do not add features, defaults, or docs
  that imply raw audio binary streaming is safe over the open internet.
- The plugin falls back to `mycroft.conf` when no `binary_protocol` config
  block is given — preserve that fallback path when touching config loading,
  it is relied on by existing deployments.
